# ProjectEldrun — Frontend File Map — rationale archive (`src/`)

Frozen snapshot (2026-09-18) of the long-form rows that `docs/filemap_frontend.md`
once carried: the incidents, measurements and rejected alternatives behind each
file. **Not maintained** — grep it for *why* something is the way it is, and
verify against the code. New rationale goes in code comments or `docs/context/`.

**Entry & shell**

| File | Purpose |
|------|---------|
| `src/App.tsx` | Root component, theme injection, global key handlers. |
| `src/main.tsx` | React entry point. |
| `src/crashReporter.ts` | Captures/forwards WebKitGTK renderer crashes to the backend. |
| `src/lib/rendererWatchdog.ts` | The renderer memory watchdog: reloads a window whose webview renderer passes 4 GB, before it OOM-aborts (a 44 GB leak, 2026-07-31). **Per window** — mounted in `AppShell` *and* `DetachedApp`, each acting on its own renderer and reloading only itself — because the first version read the largest renderer under the app and always reloaded the main window: with a popout holding 4.7 GB, the 1.4 GB main window reloaded itself every 30 s and freed nothing (2026-09-01). **Which renderer is ours is probed, not asked**: no engine we ship on will say (WebKitGTK 2.52 dropped `webkit_web_view_get_web_process_identifier`; WebView2/WKWebView never had one), so a window samples every renderer's RSS (`webview_renderer_rss`), allocates and touches a 192 MiB buffer, samples again, and the pid that grew by that much is its own — once per window (cached in `sessionStorage` across our own reloads; the process is the same), then *claimed* with the backend (`webview_renderer_claim`) so every window's readout can name the others. One renderer needs no probe; an ambiguous probe retries at the next poll, three times, then the window falls back to the largest renderer. A reload is also never repeated inside a 10-min cooldown (`sessionStorage`, per window): still over the ceiling right after a watchdog reload means the memory is not that window's heap. Also exports the readout helpers behind the debug footer's `RSS main 0.9 GB · win-1 4.6 GB` beside the TTY meter (`SidePanel`). Pure decision tested in `RendererWatchdog.test.ts`. Both reports end in the memory KIND (`formatRendererMemory` over `webview_renderer_memory`), silently absent on a backend that predates it. The `ipc-fallback` crash.log line comes from `embed/fileAccess.ts`'s `readFileBytes`: a raw read answered as a number array inside a real window means Tauri's postMessage IPC fallback is armed, which evaluates every PDF read as a script (measured: one 82 MB read → 2.8–6 GB renderer). |
| `src/lib/strayFullscreen.ts` | Clears a **stray OS fullscreen** — the state that quietly makes a popout unmovable (the WM drops `_NET_WM_ACTION_MOVE`, so `startDragging`'s `_NET_WM_MOVERESIZE` is refused and every title-bar/grip drag no-ops with nothing on screen to say why). Exists because the state cannot be *read*: `isFullscreen()` returns tao's cache of its own last `set_fullscreen`, never the window manager, so a fullscreen from the WM's shortcut, a page's `requestFullscreen()`, or a presenter whose cleanup never ran reads back `false` for ever. So it clears unconditionally (`gtk_window_unfullscreen()` is a no-op otherwise) and puts the judgement in the pure `mayClearStrayFullscreen`: the page's own DOM fullscreen and a running talk hold it, macOS is excluded. `fillsScreen`/`windowFillsScreen` is the free synchronous stand-in for that impossible read — a viewport covering its whole monitor — used by `DetachedCenterPanel` to keep the rescue off the ordinary drag's path. Tests in `StrayFullscreen.test.ts`. |
| `src/types/index.ts` | Shared TypeScript types. |

| `CenterPanel.tsx` | Tab/subwindow tiling host; keeps all panes mounted across scope switches. |
| `DetachedCenterPanel.tsx` | Center-panel variant rendered inside a detached OS window. Its title strip carries the #240 **fit-to-this-screen** gesture: double-clicking it invokes `snap_detached_window`, which clamps the popout to the monitor it is on and slides it fully inside — the way back for a window sized on an external display that now hangs off the laptop panel. The double-click is counted by hand from `pointerdown` rather than via `onDoubleClick`, because the first press hands the pointer to the WM (`startDragging`'s `_NET_WM_MOVERESIZE` grab) and the WM's move loop swallows the `dblclick`; `detail` is no help either, since the pointer-events spec pins it to 0. The pair is counted by `stores/detached`'s pure `decideTitlebarPress`, whose load-bearing part is the third input: a title-bar drag carries the window *under* the cursor, so the grab point keeps the same client coordinates however far the window travelled, and a drag→release→re-grab (how anyone nudges a window across a desk) is otherwise indistinguishable from a double-click — which made every quick re-grab snap instead of move, i.e. a popout that stopped answering the drag under way. A press that follows an OS `Moved` of this window is therefore a re-grab, never the second half of a double-click. And a snap that cannot happen (no `snap_detached_window` in a backend predating #240, or no monitor to fit onto) falls back to the move while the button is still down, so the strip never swallows a press. The move itself (`beginNativeWindowMove`) is **self-healing**: a window the WM holds in fullscreen has no `_NET_WM_ACTION_MOVE` and refuses the drag silently, and `DetachedApp`'s guard fires on resize and focus-regain — neither of which a window that is already stuck *and* already focused produces — so the press that discovers the problem is the one that has to fix it. The clear is **fired and not awaited**, and gated on `lib/strayFullscreen`'s free `windowFillsScreen()`: awaiting it would put a round trip in front of every drag of a merely *maximized* popout (the ordinary result of F11, which Muffin moves perfectly well) to buy nothing in the case that is not stuck, so the ordinary drag stays exactly as immediate as it was and the worst case left is a stuck window that takes a second press — by which time the fullscreen is gone for good. |
| `DetachedApp.tsx` | Root component for a popped-out/detached subwindow (#42). Also holds the **no-fullscreen guard**, which is what keeps a popout movable at all: a window in `_NET_WM_STATE_FULLSCREEN` loses `_NET_WM_ACTION_MOVE`, so the WM refuses the `_NET_WM_MOVERESIZE` that `startDragging` sends and both the titlebar drag and every tab bar's grip silently no-op (observed under Muffin; `restore_main_window` documents the same under KWin). A popout has no OS title bar, so nothing on screen tells a fullscreen one from a merely large one — it just stops being movable. Hence F11 **maximizes** here (`DetachedCenterPanel`) rather than fullscreening, and this component clears a stray fullscreen as the net under that. The guard runs **continuously** (debounced on resize — every fullscreen transition is one — plus focus regain), not only at mount, and it **clears without asking**, which is the half that took two goes to get right: `isFullscreen()` never reaches the window manager. tao hands back the value its own `set_fullscreen` last wrote, so a fullscreen arriving from anywhere else — the WM's shortcut, a page's `requestFullscreen()` (WebKitGTK fullscreens the toplevel for it) whose element was then destroyed, a presenter whose cleanup never ran — reads back `false` for ever and a guard gated on that read does nothing, which is how a popout was found sitting fullscreen and immovable with this very effect mounted. `setFullscreen(false)` maps onto `gtk_window_unfullscreen()` unconditionally and is a no-op otherwise, the same read-free way `restore_main_window` clears the main window's. What must *not* be cleared — a talk in progress, the page's own DOM fullscreen — is `lib/strayFullscreen`'s pure `mayClearStrayFullscreen`. The continuous schedule matters for the same reason it always did: a mount-only check could not see the one path that still fullscreens a popout deliberately: `DeckPresenter` fullscreens the window it presents in and undoes it in its cleanup, so a presenter torn down without that cleanup (a webview reload, an HMR module swap in dev, a crash mid-talk) left the window immovable with no control anywhere that brought it back — F11 maximizes, and a maximize leaves a fullscreen window fullscreen. A talk in progress is skipped via `stores/presentation`'s `presenting`, since that window is fullscreen because the user asked. macOS is excluded, the exclusion `restore_main_window` makes. Group B made it the popout's *window* owner too: it installs the `stores/detachedContext` seam (so panes' tab writes are forwarded rather than dropped), subscribes this window's settings store to `SETTINGS_CHANGED` (its snapshot was taken once at mount, which is how a popout's own write used to spread a stale copy back over `settings.json`), adopts the tab statuses the host mirrors over, seeds the popout's projects store from the seed (which is what makes a *local* project's file views resolve a project at all), mounts `HpcGuardDialog` and `ScreenshotSaveOverlay` (both answer where the action was started — the guard used to park a Promise nobody in this window could resolve), polls its own window visibility so a parked or minimised popout stops streaming and polling, and raises `DetachedCloseChoice` on the WM ✕ instead of discarding the tabs. |
| `DetachedCloseChoice.tsx` | What the WM ✕ on a popout asks (Group B #237): put the tabs back in the main window, close them for good, or cancel. Closing used to discard them outright — PTYs killed, nothing restored — while there was no dock-back gesture at all, which made the most reachable control on the window also the only irreversible one. Neither outcome is a safe default, so the window asks; cancel is the right answer to a misclick. Sets an explicit color, the portaled-dialog rule: a popout is its own document and `body` has none. |

| `ProjectDialog.tsx` *(in `projects/`)* | New/Import project dialog incl. SSH + OpenVPN + scaffold-fill sub-flows. An import's source is a local folder, a GitHub/GitLab **clone** (`git_clone` lands the tree, then the ordinary import registers it in place), or a **fork** of one (`git_fork_clone` — the same landing, preceded by creating the user's own copy on the host so the project has something to push to, with the original left as `upstream`). Also asks the **project-container** question here rather than only in the pill menu, because this is the one moment it is free (flipping it later restarts every tab): the row defaults **on for an import** — folder, clone or fork, i.e. code nobody has read yet — and **off for a new project**, with an explicit choice sticking; it runs the pill's own `set_project_sandbox` + preflight before the project reaches the store, so activation warms the right container. Fork adds only a *Host type* row (detect-from-URL / GitHub / GitLab: a self-hosted host names neither, and the provider decides which CLI runs) and a `gh`/`glab` install banner; every other branch is the clone's, since a fork import *is* a clone import. Also **pre-checks whether the site is already a project** (#152) as the folder/host path is picked, via `check_project_site` — the *same* resolver the backend refuses with, so the warning and the refusal cannot disagree. It is advisory (the list can move under it) and the write-side gate is the real one, but it is what stops a clone or fork from downloading a whole repository into a destination that is about to be rejected; a missing command resolves to "no conflict" rather than blocking a dialog against an older backend. The notice names the colliding project and offers to **open it**, because a dead-end error would leave the user to go find it. The site it checks mirrors the backend's: the host path when remote, else the folder the project ends up in — which for a *copy* import is the destination, not the source it copies from. The container row grew into the **three-way trust tier** (Local / Container / VM, `docs/vm_projects_plan.md`): the VM option is offered only when `vm_doctor` passes and only for a new project or a plain clone import (a folder/fork import would need a host→VM data move v1 doesn't do); an import *recommends* the VM when available, falling back to the container as before. A VM submit skips the local create path entirely — `create_project` with a `vm` spec, boot, then for a clone a **visible tab running `git clone` inside the VM** through a temporary proxy allow, so the untrusted bytes never land on the host. When the doctor reports missing *packages* it also carries an `install_command`, offered as the ordinary one-click install tab (with a re-probe loop while it runs, so the tier appears without reopening the dialog); what a package manager cannot fix — `/dev/kvm`, disk space — stays a sentence and carries no button. The **Git hosting field is filled from the repository a clone/fork import comes from**, not from a fixed default: the provider comes off the URL's host and public/private from the backend's anonymous `git_remote_visibility` probe (debounced on the URL), the hint names where the answer came from, and the resolved provider is passed to `import_project`/`create_project` as `gitProvider` so the project is badged by its actual host instead of waiting for the `origin` sniff. An answer the user gives in the dropdown themselves is never overwritten. |

Every settings surface — this dialog, its sub-panels, `UpdatesPanel`, `MobileSettings`, and the settings-shaped sections other dialogs embed — is made of these and nothing else, because the alternative is what was there before: bordered cards alternating with bare rows, so half the controls sat inside a card edge and half sat flush with the dialog padding; each `Dropdown` sized to its own longest option, so no two shared a right edge; `.settings-row input` matching **no rule at all**, so several fields rendered as raw native inputs; and help paragraphs floating between rows, belonging to nothing. | `ThemeCustomizer.tsx` | **The Theme Customizer** — the whole color palette as one editable list, opened from Settings → *Theme colors* and rendered *instead* of the Settings dialog (‹ Back returns), so the palette being edited is not judged through the scroll sitting on top of it. One row per CSS variable — swatch, the token's **name** (this panel edits the design system, so the name is the honest label) with an **example** under it of what visibly changes when that token does (the name says where a value sits in the system, which is not what anyone here is asking; keyed off the name by `themeTokenExampleKey`, so a catalog entry cannot arrive without one), an editable hex, a per-token reset — plus the corner-style knob, the accent picker (both moved out of the Settings panel) and the mouse-cursor pack (`lib/cursorPacks`, previewed in the row with the very images the pointer is drawn from) — those two shape and color the same chrome, and Settings keeps a single row pointing here. Two things carry it. **A token's current value cannot be read**: `getComputedStyle` hands back a custom property's *token stream* (`color-mix(…)`, a `var()` chain, a gradient), not a color, so each swatch is resolved by PAINTING it — a hidden probe takes `color: var(--token)` and its computed `color` is read back, with a sentinel on the probe's parent catching the values that are not colors at all (the fancy themes' gradient `--bg-header`), which fall back to the token's `probe` twin. And **edits preview immediately, persist debounced** (400 ms), the bargain the accent picker already makes — a color input fires dozens of events per drag and each commit is a settings.json write plus a cross-window broadcast. The accent row alone writes `ui_accent` rather than the map — that color already has a cross-theme setting whose derived hover/active/pill family rides along, and two settings writing `--accent` would be two sources of truth for one color — and it keeps the swatch strip instead of a hex field, since the presets are the control most of the time and its "Theme default" is already that row's reset. Two things ride on the same readback. **Saved themes** (`Settings.ui_theme_presets`, validated by `stores/settings.normalizeThemePresets`) put the whole look away under a name — base theme, accent, the token map and the corner style, because a palette without its base theme comes back as a different look — and Load writes all four in one `updateSettings` patch, dropping any color edit still on the debounce, since that edit belongs to the look being replaced. A preset is validated on **read**: settings.json is hand-editable and Load is one click away from being an arbitrary-CSS-variable write. And **"Colors in this theme"** is the painted palette deduplicated (`paletteFromColors`) — every distinct color the document shows right now, overrides included — offered as a strip that *expands* the row rather than floating over it, because the card sits in a scrolling dialog where a popover is one scroll from being clipped. |
| `UpdatesPanel.tsx` | **Settings → Updates** (Group H #209b): is there a newer Eldrun on the project's GitHub releases page, and install it. It checks **on mount**, which is the one place an automatic request is honest — the user navigated to a screen whose entire subject is that question; nothing else here polls and Eldrun never checks in the background. The three-step shape (check → download → install) is deliberate rather than one button: the middle step takes minutes on a 150 MB artifact and the last one closes the app on two of the three platforms, so the user who has just read what changed is the one who decides when. **No path and no URL is ever sent** — `download_app_update` and `install_app_update` take nothing, the backend re-checks and installs what it staged. The release body renders as the plain text it is; no markdown parser is run over text fetched from the network. A `manual` install (a `.deb` or package-managed copy) is offered no install button at all, only where the file went, and **no branch here relaunches Eldrun**: a window holds live terminals and open tabs. Tested in `src/__tests__/UpdatesPanel.test.tsx`; untested live. |
| `layout/AgentContinueHost.tsx` + `stores/agentContinue.ts` + `shared/usageReport.ts` | **Auto-continue** — one switch per agent tab (the ⟳ Continue chip in the Agents view) that keeps it going across its CLI's *own* rate-limit windows. The loop is: read the agent's usage panel (`agent_usage` — the client-side `claude -p "/usage"` run the phone's status sheet already uses, which spends no quota and needs no tab), place the **soonest** rollover the panel names in time, submit one `continue` a minute after it, then read the panel again — which now describes the fresh window — and arm the next one. Three things it deliberately is not. It is **not a scheduler**: nothing is written to `agent_tasks.json`, because a rule the user never made has no business sitting in the tab's schedule menu beside the ones they did — the only persisted trace is `TabEntry.autoContinue`, and the arming time is live-only (a stored one would fire against a window that turned over while Eldrun was closed). It **chooses nothing about the agent**: one word, through `lib/scheduledAgentInput`, the same path a scheduled prompt takes, which is what keeps the permission mode the agent's own. And it **never guesses at a time**: `resolveResetAt` recognizes the shapes Claude Code actually prints (`6:20pm`, `Mon 9am`, `tomorrow 09:00`, `18:20`) and refuses everything else — a bare number is a day, not an hour, so a calendar date is answered `null` rather than read as 3 a.m. — after which the row says *why* there is nothing armed rather than sitting silent, the failure mode a switch that is on and quietly doing nothing would have. The parser moved from `mobile-web/src/terminal/` into `shared/` for this: one reading of the panel, so the phone's bars and the laptop's countdown cannot disagree. Delivery reuses the scheduler's idle/decision/settle gate with **one** deliberate loosening (`deliverable`): a tab whose output the activity store has never seen — an ordinary restored agent tab — counts as quiet rather than as not-yet-settled, because a missed rollover here is not retried in an hour but at the *next* reset hours later. Every send writes a Sent-prompts row, since an unattended prompt that leaves no trace is a tab that answered something nobody can find. Tested in `AgentContinueHost.test.tsx` + `UsageReset.test.ts`; untested live. |
| `mobile/MobileSettings.tsx` + `mobile/MobileBridgeHost.tsx` | Eldrun Mobile desktop surface (`docs/eldrun_mobile_agent_plan.md`): host/Serve/pairing/device/project controls plus the narrow event bridge that catalogs permitted agents, idempotently creates typed shell or resumable-agent tabs, and supplies the Alerts snapshot. That snapshot is display-only but for one write: each row carries an opaque `alert_id`, and `alert_resolve` presses the strip's own ✓ through `lib/alertDone` — the same function the desktop group's button calls, so "what Done means for a meeting" has one answer rather than one per surface. The row is resolved by re-deriving the handles over the live feed (the mail routes' rule: an opaque id is resolved by re-reading what issued it), and the answer is the snapshot minus the row just ticked — this handler runs outside React, so the feed's own recompute has not landed yet and a re-read here would hand the phone back the row it just finished. That snapshot is read with `useAlertsFeed({ ignoreVisibility })` while the Mobile host is on: `files_alerts` is the *file viewer group's* visibility, and the phone is a surface with its own Alerts screen and no 🔔 of its own, so closing the strip beside the tree on the laptop must not blank it. The source switches, lookahead and mutes are still shared, so the two surfaces never disagree about the rows. It also applies the phone's tab renames (`rename_tab` → `renameTabInScope`), re-checking the label rule the sidecar already applied because the bridge is reachable without that route, and its tab **closes** (#31ab, `close_tab` → `removeTabInScope`, for a shell tab as much as an agent one). Its tab **colours** too (#264, `color_tab` → `setTabColorInScope`), for any tab the phone lists: the palette id is re-validated here (`isTabColor`) because the bridge is reachable without the sidecar route that already checked it, and the scope is restored and persisted for exactly the three reasons the close below spells out. Two things make a close from a phone different from the desktop's own ×, and both are handled here rather than in the store: the scope is the one the *phone* is looking at, which need not be the one the window is showing (hence the scope-aware action), and the write has to reach disk — CenterPanel persists the active scope alone, so the handler writes the layout itself (`persistScopeLayout`) or the sidecar's catalog, read out of that same session file, would keep listing the closed tab. A project the desktop has not restored this session is restored first (`restoreProjectScope`), which reads that file **without** activating the project: the switcher stays where the user left it, and an inactive project's panes are not rendered, so nothing spawns a terminal on the way. Closing stays the desktop's own non-destructive close (`lib/closeRemoteTab`) — the tmux session behind the tab keeps running — so a tap on a phone cannot end a running agent. One `mobileProject` gate decides what the phone may touch at all — Mobile access on, and not remote/sandboxed/VM, Trash excepted — so no handler can drift from the others. It never exposes paths, argv, or raw source ids to the phone. `agentStatusFor` (#31t) answers the phone's status chip and is deliberately two sources: the state and the day's tally are the desktop's own and cost nothing (the activity store's classification of that tab's output, and `usage_summary`'s counters for today's UTC bucket — the same bucket the recap calls "today"), while the quota panel is the CLI's, read by `agent_usage`, which may run it once. Neither read may take the sheet down with the other, so both are caught: a failed usage run still leaves a status worth showing. The tally is passed on **at the grain it is recorded** — `agent.prompt.<cmd>` is this agent's, while worked seconds, decisions and finished turns are the project's, covering every agent tab in it — and the phone's wording says so rather than attributing all four to the one agent the sheet is about. `desktop_images`/`attach_desktop_image` (#31u) are the bridge's inbox door from the desktop side: eligibility is checked here, and the folder scan, clipboard read and inbox write are the backend's (`mobile_desktop_images`/`mobile_attach_desktop_image`), whose `Err` is a wire code the phone maps to a sentence. **A box is a scope of its own here too** (#31aa): the settings card lists every box under **Box access** (`stores/boxes.setBoxMobileAccess` → `set_box_mobile_access`, which also resolves the box folder), and the bridge resolves the `box:<id>` id the sidecar hands it through `mobileScope` beside a project id — the box's own switch is the one consent, never a member's — while `CenterPanel` lets that switch stand in for the project's in the agent-tab tmux wrap. |
| `SidePanel.tsx` | File-tree overlay panel. A thin host: its whole file *viewer* is the shared `files/ProjectFilesView` (same component the Files (Project) tab renders). It owns only what is panel-specific — the active-project identity it forwards, the browsed-folder in the projects store, and the three window-chrome fragments it injects as slots (📌 pin, the resize border, the "Hidden subwindows" list). That folder had a control terminal and no file view, so the one way to see what was in it was `ls`; with the panel it gets the whole viewer, which is what makes it usable as one — the tree, drag-and-drop, the 📥 Downloads section (drop a download straight into it) and the tree's own "Send to project…" for the moment a file does find a home. Two things a project has are absent by construction rather than by a special case: no ⚙ project settings (`projectId` is null — there is no `project.json` to write), and no persistence of the browsed folder (`setSidePanelFolder` saves through the owning project's `project.json`), so the root's folder is session-only. `AppShell`'s `panelTarget` is what admits the scope at all. |
| `RootOverlay.tsx` + `stores/rootOverlay.ts` | **The root console** (Ctrl+Shift+R, `docs/context/root_console.md`): the root scope as one floating subwindow instead of a scope to switch to. Its panes are attach-only views of the root tabs' PTYs. Its always-mounted host persists the root scope and merges `root-mcp-changed` rows into the calendar store and `notifyCalendarWrite`, both while closed. It is the one overlay onto the root terminal: the scope chip's Root entry opens it, and `openTabInRootConsole` is the door for every flow that runs something there on the user's behalf — a one-click install (`runInstallInTab`, which used to float a second overlay of its own, `InstallOverlay`) and a parked login (`openConnectionInRoot`). The door restores root **before** adding the tab, or the new scope key would read as hydrated and the persist would write the lone tab over the saved layout. `CenterPanel` hides its own root panes while it is up. Each kind is resolved on its own terms and **none of them deletes anything** — a card is completed through `toggleTaskDone` so it also lands in the board's configured Done column; a mail has its *local* priority mark cleared (`mail_priority_set` never touches the network, so Done means "stop shouting at me", not read/archived/deleted) and `stores/todo`'s cached list is re-read or the row survives its own dismissal; an event has no completion state — an appointment is not a task — so Done is the strip's persisted mute, which takes the row out of the feed and leaves the meeting in the calendar. `mute` is passed in rather than reached for, because the muted list is `useAlertsFeed`'s to write. |
| `lib/alerts.ts` | The Alerts group's selectors, all pure — merge mail/events/tasks into one severity-then-time-ordered list. `now` is a **parameter**, not a `Date.now()`, for `todoBoard`'s reason: every interesting case here is a boundary case (a meeting in four minutes, a card due at midnight) and none of them is testable if the clock is ambient. Two window rules and only one is symmetric — the lookahead cuts the future at a **whole day**, since "next week" is a count of days and a rolling 7×24h would show a day-7 event at 08:00 and hide it at 10:00; there is deliberately **no backward limit**, because an overdue thing does not stop being overdue after a fortnight and the group would quietly go green while the deadline is still missed. What bounds the past is the source: a done card and a cancelled event both leave on their own. A **card** is cut again at `TASK_LOOKAHEAD_DAYS` (7, strictly), the shorter of the two windows winning: a meeting next month is a fact about the calendar and belongs in a long lookahead, a card due next month is a *plan*, and a strip of plans is a second board rather than an alert. The already-converted-to-a-card rule is `selectUrgentMail`'s, reused rather than restated, so this group and the board's rail cannot disagree about which marked mail is still asking for something. Muting is here rather than in the component for one mechanical reason: it has to happen **before** the cap (a silenced row that still consumed one of `limit` slots would mute a second thing the user never chose), which is also why the mail pre-cap is `limit + muted.length`. `selectAlerts`/`selectMutedAlerts` are the two halves of one partition of the same feed, and `selectMutedAlerts` returns only rows that are **still live** — the only liveness signal this module has, and why `addMutedAlert` *bounds* the stored list instead of pruning it. Tested in `src/__tests__/Alerts.test.ts`. |
