# ProjectEldrun — Backend File Map — rationale archive (`src-tauri/src/`)

Frozen snapshot (2026-09-18) of the long-form rows that `docs/filemap_backend.md`
once carried: the incidents, measurements and rejected alternatives behind each
file. **Not maintained** — grep it for *why* something is the way it is, and
verify against the code. New rationale goes in code comments or `docs/context/`.

**Top level**

| File | Purpose |
|------|---------|
| `main.rs` | Tauri app entry point, plugin registration. |
| `lib.rs` | Command registration (`generate_handler!`), app setup, hook/restore install. Also the crash logger: panic hook + fatal-signal handlers appending to `crash.log`. The Unix handler restores `SIG_DFL` and re-raises **itself** — WebKit's WTF signal layer chains to the handler it found by calling it as a plain function, so `SA_RESETHAND` alone never fires and a fault loops forever on its thread (a 500 MB crash.log of one repeated line and a hung window, 2026-09-05). It then writes the context a fix needs — UTC time, program counter, thread id/name, the exact executable, version — and a glibc `backtrace_symbols_fd` trace as `module(+offset)` lines under an `alarm(5)` guard, `SIG_DFL` restored *before* any of it so a fault inside the handler kills rather than loops. `scripts/crash-symbolize.sh` resolves the newest entry to file:line with `addr2line` against the binary the entry names. Keep it async-signal-safe: stack buffers, no allocation, `libgcc_s` pre-loaded at install by one warm `backtrace()` call. The webview crash reporter reloads a dead renderer under a **per-window** budget (`renderer_reload_allowed`; the process-wide static it replaced let one crash-looping popout spend the main window's reloads). On macOS it also installs the **explicit menu bar** (`macos_menu_plan`, tested on Linux): App (About, Services, Hide, Hide Others, a custom Quit that closes the main window so AppShell's teardown runs), Edit (mandatory — its Copy/Paste are how ⌘C/⌘V reach xterm), Window (Minimize, Fullscreen) — and deliberately no Close Window, whose ⌘W quit the app from a focused terminal. |
| `storage.rs` | JSON persistence helpers: unique-temp atomic replacement and serialized, corruption-preserving read-modify-write transactions. |
| `paths.rs` | Canonical Eldrun directory paths. |
| `sysstat.rs` | Per-process CPU sampling via `/proc` (`descendant_pids`), the whole-system `SystemSnapshot` behind the monitor pane, and `machine_load()` — the **aggregate-only** sample (CPU times, memory/swap, load, CPU temp) with *no* process table. That third one exists because a process walk is the expensive half: the 🧠 local-model menu polls "how loaded is this machine, and what is left for the next model" every couple of seconds while hovered, and paying a `/proc` read per process (plus the JSON for all of them) for a figure it never shows is a price only the pane's own view justifies. Each platform backend implements it beside its `system_snapshot` from the same primitives, so the two can't disagree; a target with no backend answers `supported: false` rather than zeros. |
| `gpustat.rs` | Whole-**device** GPU memory (the header row, the monitor pane, the model menu's headroom line) — Ollama's `/api/ps` figure is now one line of its breakdown, not the reading. Reports a GPU's **two** pools separately because on an APU only one is real: the dedicated VRAM carve-out (~512 MB — the framebuffer, permanently ~full, so it alone says nothing) and the shared pool mapped out of system RAM (amdgpu's GTT, where a model actually lands); callers sum them, and on a discrete card the shared half is 0 so the sum collapses to plain VRAM. Sources: **DRM sysfs** (`mem_info_*` + `gpu_busy_percent` — no tool, no root) and **`nvidia-smi`** (the only portable NVIDIA read; a process spawn, so its *absence* is remembered rather than re-paid every poll). A card is only reported when it states a `vram_total` — Intel's `i915` exposes none, and a zero is not a measurement. One ~1 s cache serves all three surfaces. Each `GpuSample` also carries the card's **sensors** — temperature, power (draw + cap), core/mem clocks, fan %, PCIe link, driver version — read from the *same* cheap sysfs (a card's `hwmon` subdir + `pp_dpm_*`/`current_link_*`) / `nvidia-smi` pass, so every surface gets them free; each is `None` when the driver won't say (never a fake zero). **Per-process** GPU memory is deliberately separate (`process_snapshot` → `gpu_process_snapshot`, monitor pane only, *not* cached into the shared snapshot): a heavier read (a `/proc` `fdinfo` walk deduped by `drm-client-id` for amdgpu, an `nvidia-smi --query-compute-apps` spawn) the always-visible header must not pay for. A **remote** project samples its host's GPUs too: `sysstat::REMOTE_SNAPSHOT_SCRIPT` ships the host's DRM sysfs files (`AMD\t…` lines) and raw `nvidia-smi` CSV (`NVSMI`/`NVPROC`) over the one SSH round-trip, and `parse_remote_snapshot` runs them through these *same* `parse_drm_card`/`parse_nvidia_smi`/`parse_nvidia_apps` parsers — so a host GPU reads field-for-field like a local one. Remote per-process is NVIDIA-only (the AMD `fdinfo` walk is too heavy to run per remote poll). |

**Commands (`commands/`)** — Tauri command handlers exposed to the frontend.

| File | Purpose |
|------|---------|
| `projects.rs` | Project CRUD, scaffold/import, time-today (god module; #1). Also the **duplicate gate** (#152): `find_project_conflict` is the one answer to "is this already a project", asked by `create_project`, `import_project`, `finish_import` and `extend_project_to_remote` so four call sites cannot drift into four definitions. It compares a `ProjectSite`, not a path string, and the distinction is the whole point — a *local* project is its directory (canonicalized, so a trailing slash or a symlink cannot smuggle a second registration past it), a *remote* one is its SSH target + host path, because its registered `directory` is a per-id state dir that never matches twice however often the same host folder is imported. A remote project's **mirror** counts as an owned tree too. `import_project` runs it **before** the mode dispatch moves anything: the check used to see only the destination, so a `move` re-import under a new name moved the tree out from under the original entry. `copy` is deliberately exempt (new directory, source left registered and intact). `check_project_site` is the same resolver as a read-only query, so the dialog can warn — and offer to open the existing project — before a clone downloads a repo that would be refused. |
| `fs.rs` | File-I/O commands (read/write/mtime, extracted from `projects.rs`; #1 seam). |
| `fs_watch.rs` | Filesystem watch start/stop + change events. |
| `git.rs` | Git status/history/commit/push. Also the **worktree** surface (#23, `docs/worktree_improvement_plan.md`), whose three non-obvious rules are all about the fact that the git verb is the easy part. **Where the operation runs is not where the bytes the user picked live**: for a remote project `project_dir` is the *local mirror*, so resolving remoteness from it alone created host worktrees at mirror-shaped paths and left the mirror's own repo unmanageable — `WorktreeSite` makes the choice explicit, following `git_publish`'s `PublishSite`. **A worktree has exactly one legitimate home**: `git worktree add <path>` creates *and populates* `<path>`, i.e. an unconstrained path argument is a "write repo-controlled content anywhere writable" primitive, including somewhere Eldrun later reads back as intent (#151) — so `resolve_worktree_path` confines every one to `<root>/.eldrun/worktrees/`, which also makes it invisible to both byte-sync walkers and *visible* inside the container (the linked `.git` file's `gitdir:` pointer resolves, because the project dir is mounted at its identical absolute path). **`worktree add` checks out, and a checkout runs hooks**: `NO_HOOKS_CONFIG` (`-c core.hooksPath=`) is pinned on these verbs and on `git_checkout`, deliberately *not* in `HARDENED_CONFIG`, which `git_commit` also goes through and where the user's own hooks are the point. `force` on remove is a **count**, not a flag — git answers a locked worktree with "use 'remove -f -f'" and exits 128 for a single `--force`. Also `git_remote_visibility`, the import dialog's public/private answer: one **anonymous** `ls-remote` (credential helper reset to empty, the stored token deliberately *not* offered — with it every repo the user can see reads as public) against the URL's https form, since an ssh URL says nothing about visibility on its own. Public = reads without credentials; an auth refusal (or GitHub's 404-for-private, indistinguishable from a typo) = private; anything else = unknown, and the field keeps its private default. |
| `git_publish.rs` | Publish a project's repo to GitHub (`gh`) or GitLab (`glab`). Owns the shared `Provider` (which CLI, which token/host env). Also owns **which side runs the CLI** (`PublishSite`), which is the one non-obvious thing here: *where the bytes are is not where the hosting account is*. `gh auth login` and the Settings → Git Hosting tokens are secrets of the local machine, while a work remote is typically a cluster login node with no provider CLI, no GitHub credentials and often no outbound https — so a remote project publishes **from its lockstep mirror by default** (`publish_from = "local"`, the dialog's "Publish from" selector), and the ssh path is the explicit opt-in for a host with its own login. The local default's one hazard is a stale mirror, so `describe_mirror_guard` (pure, tested) refuses unless lockstep is enabled *and* green — otherwise a publish would create the repo from the wrong history. Every follow-up (visibility, unpublish, and `commands::git::git_push` via `mirror_origin_repo`) routes by `origin_site`: wherever `origin` actually got wired, so the create and the pushes never end up on opposite sides. `run_remote_provider_command` additionally translates OpenSSH's own failures (`ssh_transport_error`) — `ssh_base_args` reuses but never creates a master, so a disconnected project fails at ssh auth, and "Permission denied (publickey,password)" reads like a GitHub rejection if passed through raw. |
| `git_fork.rs` | The import dialog's **fork** source: fork a hosted repo into the user's own account, then clone *that*. A fork is a server-side operation, so it goes through the provider CLI's raw `api` subcommand (`gh api -X POST repos/<owner>/<repo>/forks`, `glab api -X POST projects/<id>/fork`) rather than `repo fork --clone` — the response JSON *names* the fork, and neither CLI's clone can be pointed at a destination directory or have its namespace guessed (a fork can land elsewhere, or already exist: GitHub returns the existing one, GitLab refuses with "already been taken", which is looked up instead of reported). The clone itself is `git::git_clone_blocking`, so the URL whitelist, token credential helper and partial-directory cleanup are the ordinary clone's; it is retried only on the "not there yet" failure, since forking is asynchronous on both services. `git remote add upstream <original>` is best-effort — the tree is on disk by then. `fork_cli_available` backs the dialog's install banner. |
| `terminal.rs` | Terminal/PTY command surface (delegates to `terminal/mod.rs`). Also the **local** tmux-session commands (TODO #85): `local_tmux_{list,kill,rename}`, and the `pty_spawn` local-tmux wrap (`services::tmux_local`). |
| `app_update.rs` | **Settings → Updates**: the four commands behind "is there a newer Eldrun". Thin, like `commands::monitor` — the parsing, the URL allowlist, the staging and the per-platform install are `services::app_update`'s; this owns only the download-progress event and the rule that the *whole* flow re-checks rather than trusting the renderer. **No command here takes a URL or a path**, which is the boundary: `download_app_update` re-asks GitHub which asset belongs to this platform, and `install_app_update` installs what that download staged — so a compromised renderer can nominate neither a file to fetch nor a binary to run. Progress is emitted per megabyte, not per chunk, so a 150 MB artifact costs tens of IPC messages rather than thousands. |
| `apps.rs` | App launching, `run_script_detached`, `open_file`, external window tracking. |
| `default_apps.rs` | Per-file-type default-app mapping. |
| `ssh.rs` | SSH commands for remote projects (`ssh_connect`, `ssh_default_dir`, `ssh_list_dir`, `ssh_tooling_status`). Also the **active-disconnect** pair (explicit-click only, never on relaunch): `remote_kill_all_jobs` (`tmux kill-server` on a host — ends *every* running session/job, best-effort, rides a live master or authenticates ad-hoc like `global_machine_monitor_snapshot`) and `ssh_close_master` (`ssh -O exit` on the shared `cm-%C` socket, for a project-free global machine that pools nothing; a project host tears its pool down via `remote_disconnect` instead). |
| `remote.rs` | Pooled SSH/SFTP connection lifecycle (`remote_connect`/`remote_disconnect`) for the active remote project. Also `remote_upload_file` (HPC wizard "Load data" step, `docs/quirky-knitting-umbrella`): streams a local file to `<remote_path>/<dest_rel>` over the pooled SFTP (`upload_file_streaming_on`), primary host, dest_rel sanitized to stay inside the root. Also the tmux-session commands (TODO #85): `remote_tmux_list` (Sessions view, `tmux ls` → `Vec<TmuxSession>`; called per-host so the view aggregates every connected worker), `remote_tmux_kill` (explicit-close / per-row kill), and `remote_tmux_rename` (per-row rename), all over the pooled ControlMaster. |
| `openvpn.rs` | OpenVPN tunnel connect/store-config commands. |
| `ollama.rs` | Ollama model list/pull/delete + local autocomplete. **Where the server is** is `resolve_ollama_addr` (pure, tested) and nowhere else: `Settings::ollama_host` was declared for years and read by nothing while the transport dialled a literal `127.0.0.1:11434`, so anyone running Ollama on another port had a setting that did nothing (#201a). It is read per call — a settings write is not an event this module hears — and three of its rules are the point rather than plumbing. **`https://` is an error, never a downgrade**: this transport is a raw `TcpStream` speaking HTTP/1.0, and connecting in the clear to an address the user wrote as TLS would put their prompts on the wire while the setting says otherwise. **A non-loopback host needs `ollama_allow_remote_host`** (default false, a second key because it is a second decision — another *port* is still local inference, another *host* means every prompt and every file an agent reads leaves this machine), judged on the literal typed and never on what it resolves to. And the connect is **bounded** (4 s), which only became necessary once a remote host was reachable at all: a bare connect at a host that is off or mistyped blocks on the kernel's TCP retries for minutes, the window-freeze shape this repo has paid for before; loopback refuses instantly and never reaches the bound. `ensure_ollama_running` inherits the consequence — it refuses a remote endpoint by name rather than silently spawning a *local* server the caller was never pointed at, tries the systemd unit only for the default address (the unit binds what the unit says), and hands a spawned `ollama serve` an `OLLAMA_HOST` so a non-default port is bound rather than waited for in vain. It also **records what it started** (`OwnedServer`), because a server Eldrun brought up used to outlive it — the `ollama serve` child kept its runner and several GB of VRAM after the window was gone. `shutdown_owned_server` (from `RunEvent::Exit`, beside the terminal/OpenVPN/container teardowns) undoes exactly that much: the spawned process is TERMed **with its subtree** (the runner holding the weights is a separate process) with a short blocking grace before SIGKILL — `ReapMode::GracefulBlocking`, which exists because `Graceful`'s escalation thread dies with the app — and the systemd unit is stopped `--no-block` only when `systemctl is-active` said it was **down** before this run started it. The absent third case is the point: a server that was already listening, or one on another machine, is never recorded and so can never be stopped — Ollama is a machine service (a terminal's `ollama run`, another editor's completion plugin, a unit enabled at boot) as often as it is an Eldrun detail. `ollama --version` is deliberately **exempt**: it reads the installed binary's version, which is what the `launch` feature gate is about, and pointing it at the host costs both the documented "touches no network" property and two minutes against an unreachable one. Also the three things that have to be asked about rather than assumed — two about a *model*, one about the *machine*. **The GPU**: Ollama ≥0.32 **drops integrated GPUs by default**, logging "dropping integrated GPU; to enable, set `OLLAMA_IGPU_ENABLE=1`" and then naming `cpu` as its only inference device — so on a machine whose sole GPU is the APU, an ordinary update moves every model onto the CPU and the only trace in the API is a `size_vram` of 0, which is *also* exactly what a model too large to fit looks like. Three answers, and the split between them is the point. `ensure_ollama_running` sets the variable on the server **Eldrun itself** spawns (ours to configure; an explicit value already in the environment is left alone, because a user who set `0` meant it), which reaches nothing about a systemd-managed one. `LoadDevice` (`auto`/`gpu`/`cpu`) is the per-load choice, mapping onto the one option llama.cpp exposes for this — `num_gpu` omitted / `MAX_GPU_LAYERS` / `0` — and `auto` is a real third value rather than the absence of a choice: deferring to a scheduler that knows what else is resident is not the same act as overriding it, which is also why `Auto` omits the option instead of computing a number with strictly less information than the scheduler has. And `ollama_gpu_status` is the diagnosis, which exists because `size_vram: 0` alone cannot support one: it sets `igpu_dropped` only when **four** facts line up (a resident model with nothing on the GPU, a GPU that exists, *every* GPU here integrated, and the installed server still offering the flag — read from its own `ollama serve --help` rather than guessed from a version number, so it stays right across an upgrade mid-session), because blaming a setting for an ordinary out-of-VRAM would send the user off to reconfigure a system service for nothing. Its `fix_cmd` is a systemd **drop-in** (additive, survives the installer rewriting `ollama.service`, undone by deleting one file) handed to a terminal for the user to run rather than applied silently — it needs a root password, and a command that reconfigures a system service is one they are entitled to read first. A `gpu` load is a **request, not a guarantee**, and the two halves are why: the option can only distribute layers across the devices Ollama registered *at startup*, so a server that dropped the GPU at discovery has nothing to offload to and the load still lands on the CPU. **Capabilities**: `OllamaModelInfo` carries Ollama's own list (`/api/show`), cached against the **manifest digest** rather than the name — capabilities are a property of the manifest, so a digest read once can never need re-reading and a re-pull misses the cache by construction, which is what keeps the 🧠 menu's every-hover list from paying a round trip per model. The rule every consumer honours is that **an empty list means "could not ask", never "supports nothing"** (`model_capabilities` deliberately does not cache a failure), because the alternative is a timed-out probe silently emptying a menu. That feeds the **tool gate**: every `LOCAL_DRIVERS` entry is a tool-calling agent, so `list_local_drivers` takes the active model and withholds them from one that positively lacks `tools` — otherwise Codex-on-`deepcoder` opens a tab that dies on its first request with a raw `does not support tools` JSON error. `prepare_local_launch` refuses again (the menu is a cache; the active model changes under it) and names the models on *this machine* that would work, since a hardcoded example list would age. `driver_verdict` is the pure, tested core of both. `thinking` is the **second** capability a model can refuse and it behaves oppositely, which is the distinction worth keeping: a model without it does not merely skip reasoning — Ollama rejects the *whole request* with `"<model>" does not support thinking` — but the agent is fine, it just must not ask, so the answer changes the launch line instead of withholding the agent. Only Codex needs it (`model_reasoning_effort` defaults to `medium`, and the user's own `~/.codex/config.toml` usually sets it outright), and `qwen3-coder` is exactly the shape that made it a bug rather than a theory: it reports `tools`, so it sailed through the tool gate and died on its first turn. The load-bearing consequence is that `non_thinking_args` also means **bypass `ollama launch`** — `launch` forwards nothing to the agent (an extra flag is an `unknown shorthand flag` error) and its generated `~/.codex/model.json` + profile do not turn reasoning off — so the direct `codex --oss` invocation is the only working path for such a model, not a downgrade. That fallback also names `oss_provider` via `-c` rather than the `--local-provider` flag Codex's error suggests: an unknown *config key* is ignored by an older Codex, an unknown *flag* is a hard argv error. `non_thinking_override` is the pure core, and "could not tell" leaves reasoning on, matching the tool gate. Bypassing `launch` costs the *other* thing it was doing, which is why `wants_local_catalog` exists: `ollama launch` generates a Codex model catalog (`~/.codex/model.json`) and points the agent at it, and without one Codex says `Model metadata for '<model>' not found` and then reasons about the context window from a built-in guess — it does not know `qwen3-coder` holds 262 144 tokens, so it compacts against the wrong number, either discarding context that still fit or overrunning a window whose truncation Ollama does not report back. `write_local_catalog` writes the same document into **Eldrun's own** state dir (`codex_local/<alias>/model.json`) rather than `~/.codex`, which is another application's to manage, and reads the two model-dependent facts off `/api/show` instead of assuming them — the context window (found by `.context_length` *suffix*, since the key is architecture-prefixed, so a new model family needs no table entry) and whether any reasoning level may be offered. An unknown window is **omitted**, never defaulted: a wrong one is worse than the fallback because it is wrong with confidence. The write is best-effort — a catalog that could not be written costs a warning, and must never become a refusal to open the tab. `local_catalog_json` is pure and tested. **Update checks**: Ollama has no "is there a newer version" API — a pull just re-resolves the tag — so `ollama_check_updates` compares the digest `/api/tags` reports against the `ollama-content-digest` header the registry answers for the same `name:tag`, one HEAD per model through the same `curl` transport `fetch_registry_manifest` uses. It is **on demand only** (a button in the 🧠 menu, never a hover/timer/launch sweep), and a model the registry could not be reached for comes back with `error` set and `update_available: false` rather than dropped — "couldn't tell" must not render as "up to date". `ollama_version_status(check_remote)` is the same question about the **server itself**, and it is a separate surface because it is a different kind of fact: a server a few minor versions back is missing whole *features* rather than weights — `ollama launch` (the only wiring that stands up an Anthropic-compatible endpoint for Claude Code) does not exist before v0.15, so on an older server that agent is absent from the + menu with nothing saying why. The split is the point: `check_remote: false` is a local `ollama --version` and touches no network, so the menu can show what is installed on every open, while the newest published version costs one unauthenticated GitHub request and rides the same click. `version_is_newer` compares **numerically**, which is the whole reason it exists rather than a `<` on the strings — `"0.9.0" > "0.14.3"` as text, so a lexical compare would have announced a downgrade as an update for most of Ollama's history — and answers `None` for anything unparseable, which is reported as "couldn't tell" and never as an update. `parse_version` scans for a version-shaped token instead of taking a fixed field, because the command prefixes a warning line whenever the server isn't running. All of it is reproducible headlessly via `examples/ollama_probe.rs` (`cargo run --example ollama_probe`) — these are ordinary `async fn`s under an attribute, so awaiting them needs no window and no click, which is the only way to tell "the button is dead" apart from "it ran and had nothing to report". |
| `tex.rs` | TeX compile + SyncTeX (shell-escape defense). `compile_tex` is **async** (`spawn_blocking`): a sync command runs on the main thread, so every TeX-figure add and every Recompile used to freeze the whole webview for up to the 600 s run timeout. Full compiles on pdflatex ride a **cached-preamble fast path**: the document's preamble is dumped once into a `.fmt` under `<state>/tex-fmt/` (`mylatexformat`, the hover preview's own trick, keyed by preamble text *plus the content of every local `\input`/`.sty`/`.cls` it reads* — a build against stale macros is a wrong PDF, not a wrong hover card) and later compiles load the dump instead of re-reading the packages, which is most of a large document's recompile time. latexmk gets it via `-pdflatex=pdflatex -fmt=<key> %O %S` with the cache dir on `TEXFORMATS` (a key, never a path — latexmk re-splits that string on whitespace); the direct path passes the absolute `-fmt=` itself. Every failure degrades to the plain compile: an undumpable preamble writes a `.bad` marker, a dump that won't *load* is discarded and the run repeated once, and a dump the engine cannot *find* (an engine that ignores `TEXFORMATS`) is `.bad`-marked so it isn't retried per compile. Also home to two commands the deck presenter needs. **`synctex_page_lines`** reads the `.synctex.gz` a compile already emits (`-synctex=1` is passed unconditionally) and reports the source lines behind each PDF page — the *producer* half of a deck slide's line anchor, which `sidecar.ts` documented and consumed but nothing ever wrote, so the mechanism did not exist at runtime. It parses the file rather than shelling out to `synctex edit` per page (a 200-page plate would be 200 process spawns for one reconcile), and harvests only the **main input's** tag, because line numbers from two files are not comparable and mixing them would be an anchor that silently means nothing. **`list_fonts`** walks the platform font directories for formats fontkit can embed, returning **paths** — the frontend measures and embeds by path, since two files can claim one family name and the export would otherwise be a coin flip. **`tex_preview_snippet`** is the editor's hover preview (#tex-hover-preview) and is deliberately *not* `compile_tex` with a smaller argument. It drives the engine **directly, one pass** (a fragment has no bibliography and no cross-references to settle, so latexmk's dependency machinery is pure latency), bounds the run at `PREVIEW_TIMEOUT` rather than ten minutes (the reader is holding a pointer still), and hands the PDF back as **bytes** rather than a path — the file lives in a scratch dir under the state dir, which the confined viewer file commands cannot read and must not learn to. The split that makes it work on a real paper is where each half runs: the wrapper `.tex` and every artefact go to that scratch dir (removed before the call returns; leftovers from a crash are swept by age on the next call), while the **working directory is the document's own folder**, so a preamble's relative `\usepackage{mystyle}` / `\input{macros}` still resolve without a single `.aux` landing beside the paper. `preview_document` wraps the fragment in `\begin{preview}` under `preview.sty`'s `[active,tightpage]` — the AUCTeX mechanism — so one wrapper crops inline math, a display, an `align` and a `tikzpicture` alike; a preamble that already loads `preview` is left alone (an option clash would fail exactly the documents best prepared for previewing). **A float is the one thing wrapped differently** (`body_is_float`), and not as a matter of taste: `\begin{figure}` demands outer par mode while `\begin{preview}` has already put TeX in a box, so a float wrapped like everything else dies with `! LaTeX Error: Not in outer par mode.` and writes nothing. Floats go through the package's own `floats` option instead, unwrapped, which makes the `figure`/`table` environment itself the preview. The names are **exactly the four that option fixes up** (`figure`, `table`, and the starred pair), measured against a real engine rather than reasoned about: a `wrapfigure` is not a `\@float` and previews to no pages at all, and a `float`-package custom float — which `algorithm` and every `\newfloat` is — redefines `\end@float` past what the option patches and dies with "Extra }, or forgotten \endgroup". A float's fallback is likewise an `article` rather than `standalone`, which cannot host one for the same reason `preview` cannot. A **second pass without the author's preamble** (`standalone` + AMS) runs only when the log blames the preamble rather than the fragment (`preview_needs_fallback`), because a typo in the snippet must fail once and report rather than cost a second engine run on every hover. **The preamble is precompiled into a cached format** (`ensure_preview_fmt`, pdflatex only): almost all of an uncached hover's engine time is the engine re-loading the same fifty packages, so the wrapper's head is dumped once into a `.fmt` via `mylatexformat` (AUCTeX's preview-latex trick) under `<state>/tex-preview/fmt/`, keyed by engine + wrapper head, and every later snippet under that preamble loads the dump instead (measured ~2.4× on a realistic preamble; the win grows with preamble weight). pdflatex only because `mylatexformat` is documented-unreliable under LuaTeX/XeTeX font loading — a cached preview with the wrong fonts is worse than a slow one. A preamble that cannot be dumped writes a `.bad` marker (one failed attempt per `PREVIEW_FMT_MAX_AGE`, not per hover); a format that no longer *loads* (corrupt, or the engine upgraded under it — `preview_log_is_format_error` tells this apart from the snippet's own error) is discarded and the pass retried plain. The whole module is about which header may be believed. **Only the topmost instance is read** (headers are prepended, so the top one is the last hop's — yours) **and only if its `authserv-id` equals the account's configured one**, because position identifies a slot, not an author: without the id check a message your server never stamped presents the sender's own forgery in the top position.
